## 〇、Claude 待核对点的代码核实结论

| 核对点 | 结论 | 代码位置 |
|---|---|---|
| 逐 Topic 生成素材是全量还是切片 | **全量**：用户勾选的每份材料 `extracted_text[:40_000]` 整段注入，无切片、无相关性筛选 | `build_topic_ai_messages` app.py:2904-2911 |
| 输出是直接 XML 还是结构化中间稿 | **直接 XML**：`clean_ai_xml` 剥围栏 → `ET.fromstring` → 根标签检查，无中间稿 | app.py:3022-3060 |
| 校验检查到哪一层 | **仅三层**：可解析、GUID token、TODO 占位符计数；无 DITA 结构、无写作规则、无跨 Topic 检查 | `validate_topic_xml` app.py:1645-1671 |

结论：Claude 的 4 条推断全部成立，对应条目**不降级**。

## 一、第一批：可靠性地基（P0，先做，改动小）

**1.1 全局上下文预算闸门**
- 问题：各段各有上限（Skill 单个 2MB、附件 60k/Skill、素材 40k/份不限份数、语料 70k、基线 60k、previous 60k），无总预算，不感知模型上下文窗口，拼出的 prompt 可超限。
- 方案：统一 `build_prompt_context()` 入口，按 token 估算（中文 ≈1.5 字符/token）设总预算，分配权重：素材 > Skill > 基线 > 语料 > previous_xml；超限时按权重裁剪并记录裁剪明细到生成结果。
- 位置：app.py:2887-2967、2553-2631、3121-3200。

**1.2 `finish_reason` 检查**
- 问题：max_tokens 截断（框架 9000 / Topic 6000）时报"XML 无法解析"，误导排错。
- 方案：`call_ai_text` 读取 `choices[0].finish_reason` / Anthropic `stop_reason`，`length` 时报"输出被 max_tokens 截断"，并允许配置调大。
- 位置：app.py:2970-3019。

**1.3 解析失败错误回喂重试**
- 问题：JSON/XML 解析失败、根标签错误 → 一次失败直接 RuntimeError。
- 方案：失败时把错误信息 + 原输出回喂模型重试 1–2 次（"你上次输出有以下错误……只返回修正后的完整结果"），仍失败再交人工。与第三批 6.1 闭环共用机制。

**1.4 框架/分析启用 JSON mode**
- 方案：OpenAI-compatible 加 `response_format={"type":"json_object"}`；Anthropic 用 prefill（`assistant` 首条以 `{` 开头）。保留现有 `clean_ai_json` 作兜底。

**1.5 GUID 正则收紧**
- 问题：`GUID(?:-|=)[A-Z0-9-]+` + IGNORECASE 误伤英文正文（如 "GUID-based"），且作用于 Skill 名称/描述/素材等宽泛入口。
- 方案：收紧为 KC 实际格式，如 `GUID-[0-9A-Fa-f]{8}(-[0-9A-Fa-f]{4}){3}-[0-9A-Fa-f]{12}|GUID=[0-9A-Fa-f-]{8,}`；`sanitize_text` 只作用于最终 XML 与用户可见字段，不碰 prompt 中的原始素材。
- 位置：app.py:70、244-247。

## 二、第二批：生成协议改造（决定可靠性上限，建议先拿 Task 做原型）

**2.1 结构化中间稿 + 模板渲染**（Claude #1）
- 方案：Task 输出中间稿 `{title, shortdesc, prereq[], context, steps[{cmd, info, stepresult}], result}`，由代码模板渲染 XML——转义、嵌套、`p` 包裹、步骤顺序全部代码保证；Concept 同理（`sections[{title, level, paragraphs[]}]`）。校验从"解析得通"升级为"规则全过"。prompt 仍附带 Skill，但模型只负责填内容。
- 收益：同时消灭转义错误、结构错误、步骤数不足三类高频问题。

**2.2 "待确认"事实占位机制**（Claude #2）
- 问题：素材没写的内容模型会补全；现在只有 `TODO_IMAGE`/`TODO_REF`，缺"缺事实"这一类。
- 方案：新增 `TODO_CONFIRM` 占位 + 中间稿字段 `unconfirmed[{claim, reason}]`；生成结果汇总为独立"缺料清单"（并入项目级 questions 视图），不混在 XML 里。系统提示从"不要编造"升级为"凡素材未确认的事实一律 TODO_CONFIRM 并登记"。

**2.3 素材切片与段落级溯源**（Claude #2）
- 方案：框架生成时为每个节点登记来源素材的章节/片段（起止偏移）；Topic 生成只注入关联片段（保留前后 1–2 段上下文），全量素材作为可选兜底。生成结果的段落带 `source: {material_id, offset}`，审核 UI 可点开对照。
- 依赖：与第三批 3.1 框架节点元数据一起做。

**2.4 版本更新/Topic 优化改为结构保留编辑**（Claude #4）
- 问题：这两种模式输入是真实 KC XML（GUID、conref、ishcondition），现有流程全量重生成 + `sanitize_text` 先破坏输入，产出无法回灌 KC。
- 方案：解析原 XML 树 → 只把需要改动的节点（正文 section/step）文字部分抽出来给模型改 → 代码回填到原树，属性、GUID、conref 原样保留 → 输出前后 diff 供人工确认。`sanitize_text` 不再作用于该路径的原始 XML。

## 三、第三批：一致性与流水线

**3.1 框架节点元数据 + 弃用行号关联**
- 问题：`framework_node_key = "line:${node.lineIndex}"`（app.js:2277），框架一编辑行号位移，批量生成会重复建 Topic；节点无类型/来源/状态元数据。
- 方案：节点结构升级为 `{id, type, level, title, summary, source_refs[], status, refs[]}`；既有关联迁移到稳定 id。分析 → 框架 → Topic 做成"每阶段确认后下游只消费确认结果"的流水线（Claude #5）。

**3.2 兄弟章节上下文注入**（Claude #3 + 本地发现）
- 方案：Topic prompt 注入父章节标题 + 同级 Topic 的标题与 shortdesc 清单，并注明"这些内容由其他 Topic 承担，不要展开"。

**3.3 项目级术语表**
- 方案：从素材/已定稿 Topic 抽取"术语 + 界面名称 + 参数名"候选表，用户确认后项目级固定，每次生成注入，并作为跨 Topic 检查的基准。

**3.4 跨 Topic 一致性检查**
- 方案：全部生成后跑一次：同一参数/控件名拼写是否一致、`TODO_REF` 目标能否在框架中匹配、标题是否重复。

**3.5 批量生成下沉后端**
- 问题：前端串行 for 循环（app.js:2479-2510），关标签页即断，后端 `BoundedSemaphore(2)` 并发没用上，任务不落盘。
- 方案：新增批量 Job：一次提交节点清单，后端逐个生成、逐个落盘、记录每项状态，支持断点续跑与进度查询。

**3.6 框架材料淘汰明示**
- 问题：框架 prompt 的 180k 预算耗尽后，后续材料只留一行"未送入 AI"（app.py:2574），整份材料无声缺席。
- 方案：被淘汰的材料列表回传 UI 明示，计入缺料清单。

## 四、第四批：校验闭环与质量保障

**4.1 生成 → 校验 → 自动修复 → 人工审核闭环**（Claude #6）
- 方案：校验错误列表 + 原稿回喂修复（限 1–2 次），复用 1.3 机制；仍失败进入人工审核队列并在 UI 标注错误项。

**4.2 校验规则引擎（含风格 lint）**
- 方案：把 Skill 中机器可查规则代码化：Task 步骤 ≥2、shortdesc ≤3 句且不含 image/xref、块级文字必须在 `p` 内、"点击"→"单击"、句长 >40 字、缺"您"、全角标点、数字与单位空格、残留占位符、concept 必有 conbody。lint 结果不花 token，替代模型自检。

**4.3 Skill 注入治理**（Claude #7）
- 方案：按 Topic 类型路由规则段（Concept/Task 各取所需）；Skill 总长度预算并入 1.1；内置与自定义 Skill 冲突时做关键词级检测并提示。快照记录从 `updated_at` 升级为**内容哈希 + 版本号**（解决内置 Skill 未覆盖时 `updated_at=None` 无法追溯的问题，app.py:636、651）。

**4.4 示例检索 + 回归集**（Claude #8）
- 方案：用 `XML素材/` 与"结构指纹"文档按类型检索最相近的已定稿 Topic XML 作为 few-shot 示例注入；建回归集（已发布 Topic + 当年素材 → 重生成 → 对比结构指纹与校验通过率），后续改 prompt/换模型/改 Skill 用数据评估。

**4.5 生成记录可复现**（Claude #9）
- 方案：每次生成落盘：模型与参数、Skill 哈希快照、素材切片标识、完整 prompt、原始返回、`usage` token 计数（当前被丢弃）。存 `data/` 本地，注意体积控制（原始 prompt 可压缩存储或只存哈希+摘要）。
